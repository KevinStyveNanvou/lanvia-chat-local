# LANVIA wire protocol v1

Status: implementation specification. This document and `lanvia-protocol.json` are the common source of truth for Desktop and Android. Numeric constants are generated by `scripts/generate-protocol.mjs`; neither client owns a private variant.

## 1. Architecture and invariants

Every LANVIA installation is a peer. It runs, subject to OS lifecycle rules:

1. an mDNS/DNS-SD advertiser/browser for `_lanvia._tcp`;
2. a UDP discovery listener/announcer;
3. a WebSocket control server and client;
4. an HTTP binary-transfer server and client;
5. persistent local identity, trust, message and transfer metadata stores.

There is no coordinator, cloud service, Internet fallback, account, or renderer-owned network socket. WebSocket carries small control JSON only. HTTP carries file bytes. Discovery is advisory: identity is confirmed on the WebSocket before privileged operations.

### Default ports

| Role | Transport | Default |
|---|---|---:|
| Control | TCP/WebSocket | 53211 |
| Transfer | TCP/HTTP | 53212 |
| Discovery | UDP | 53213 |

Ports may be changed by the user only as one coherent local configuration. The actual control and transfer ports MUST be advertised in both mDNS TXT and every UDP hello. A peer MUST connect to advertised values, never assume that a remote uses its own local settings. A bind failure is visible as `port_unavailable`; a service MUST NOT silently select an unadvertised port.

If the configured **transfer** port is occupied, the transfer server tries at most the next 20 TCP ports (skipping the locally reserved control/discovery numbers), then an OS-assigned ephemeral port as a final fallback. This is never silent: diagnostics and logs show `configured → actual`, and UDP, mDNS, `device_hello`, `device_info`, and every `transfer_request` advertise the actual bound port. Control and discovery listeners do not silently move because they are bootstrap endpoints.

## 2. Common encodings

* JSON is UTF-8. Unknown object fields are ignored for forward compatibility; required fields and enum values are validated.
* UUID values use canonical lower-case UUID strings where generated by LANVIA. Receivers treat IDs as opaque strings after length/format validation.
* `timestamp` is Unix epoch milliseconds UTC.
* File sizes and byte counters are non-negative JSON integers. v1 limits files to 1 TiB. Dart and JavaScript can represent this exactly.
* SHA-256 is 64 lower-case hexadecimal characters.
* MIME values are hints only and never authorize execution.
* IP address is learned from the received datagram/socket. A claimed address in JSON MUST NOT override the transport source address.

## 3. Identity

```json
{
  "deviceId": "dd39b0d6-9af8-47ca-bf6f-cef126260bde",
  "deviceName": "Kevin-PC",
  "deviceType": "desktop",
  "platform": "windows",
  "appVersion": "1.0.0",
  "protocolVersion": "1"
}
```

`deviceId` is generated once and persisted. `deviceName` is user-editable. v1 device types are `desktop` and `mobile`; platforms are `windows`, `macos`, `linux`, and `android`.

## 4. Discovery

### 4.1 mDNS/DNS-SD

Advertise `_lanvia._tcp` (DNS-SD form `_lanvia._tcp.local`) on the actual control port with TXT records:

* `id`: device ID
* `name`: device name (UTF-8 subject to TXT limits)
* `type`: device type
* `platform`: platform
* `version`: app version
* `protocol`: `1`
* `control`: actual control port
* `transfer`: actual transfer port

Browsers resolve A/AAAA and use only private/link-local LAN addresses. mDNS is an optimization, not a requirement.

### 4.2 UDP fallback

Each peer binds UDP `0.0.0.0:discoveryPort` with address reuse where supported. On start, network change, manual refresh, and every 5 seconds it sends a compact `device_hello` discovery object to:

* every directed broadcast reported by active non-loopback IPv4 interfaces; and
* `255.255.255.255` as a fallback.

Packet shape:

```json
{
  "lanvia": true,
  "version": 1,
  "type": "device_hello",
  "identity": {
    "deviceId": "dd39b0d6-9af8-47ca-bf6f-cef126260bde",
    "deviceName": "Kevin-PC",
    "deviceType": "desktop",
    "platform": "windows",
    "appVersion": "1.0.0",
    "protocolVersion": "1"
  },
  "controlPort": 53211,
  "transferPort": 53212,
  "timestamp": 1786723200000
}
```

Maximum accepted datagram size is 16 KiB. Invalid, oversized, incompatible, and self (`deviceId == local.deviceId`) packets are ignored. A peer is `available` until 15 seconds after its last valid mDNS/UDP sighting. Receipt triggers one unicast copy of the local hello to the source address, rate-limited to once per peer per 5 seconds; this makes asymmetric hotspot broadcast more likely to converge.

Manual connection by IPv4/IPv6 literal or hostname plus control port is mandatory. After WebSocket hello, its identity and advertised transfer port replace provisional manual metadata.

## 5. WebSocket control

Endpoint: `ws://<peer-address>:<controlPort>/v1/control`.

Every peer hosts and can initiate. To reduce duplicate automatic sockets, the peer whose `deviceId` sorts lexicographically lower initiates the automatic connection. A manual user action may initiate either way. If two authenticated sockets exist, both peers keep the socket whose deterministic key (`initiatorDeviceId`, then connection nonce) sorts lower and close the other with code 4001.

The first application message MUST be `device_hello`, within 5 seconds. The receiver answers `device_info`. Until hello succeeds, only `device_hello`, `device_info`, `ping`, and `pong` are legal. Until pairing succeeds, pairing messages are also legal; text and transfer operations require trust.

All messages use this envelope:

```json
{
  "version": 1,
  "type": "message_send",
  "requestId": "a65db7c0-82d2-44c1-bd5b-b88e72abdd32",
  "senderId": "dd39b0d6-9af8-47ca-bf6f-cef126260bde",
  "receiverId": "ef098f4f-aec0-4412-bd1a-0bdb8219108e",
  "timestamp": 1786723200000,
  "payload": {}
}
```

Rules:

* `version`, `type`, `requestId`, `senderId`, `receiverId`, `timestamp`, and object `payload` are required.
* `requestId` uniquely identifies a request and provides idempotency. Receivers retain recently handled IDs for at least 10 minutes.
* `senderId` MUST match the socket identity; `receiverId` MUST equal the local device ID.
* Maximum text frame size: 1 MiB. Binary WebSocket frames are rejected.
* Ping every 15 seconds; no matching pong in 10 seconds closes the socket.
* Reconnect delay sequence: 1, 2, 4, 8, 16 seconds; 16 seconds repeats while the peer remains discovered/trusted. Network change resets the sequence.
* Close codes: 1000 normal, 1002 malformed protocol, 1008 policy/auth, 1009 too large, 4001 duplicate, 4002 network changed.

## 6. Payloads

### Device handshake

`device_hello` payload:

```json
{
  "identity": { "deviceId": "...", "deviceName": "...", "deviceType": "desktop", "platform": "windows", "appVersion": "1.0.0", "protocolVersion": "1" },
  "controlPort": 53211,
  "transferPort": 53212,
  "connectionNonce": "e72f61a9-7af0-48cf-9c69-e1ff1369009b",
  "trustToken": "optional-base64url-token"
}
```

`trustToken` is the shared token established during pairing. Absence or mismatch means untrusted, not a failed transport handshake. `device_info` has the same fields plus `trusted: boolean` and omits `trustToken`.

### Pairing

`pair_request`:

```json
{ "pairId": "uuid", "identity": { "deviceId": "..." }, "expiresAt": 1786723260000 }
```

The receiver displays local confirmation. Requests expire after 60 seconds. Accepting generates 32 cryptographically random bytes encoded base64url. Both sides persist the resulting shared token associated with the exact device ID.

`pair_accept`:

```json
{ "pairId": "uuid", "trustToken": "base64url", "deviceName": "Kevin Phone" }
```

`pair_reject`:

```json
{ "pairId": "uuid", "reason": "user_rejected" }
```

A trust token is a LAN access control measure, not protection against a packet-sniffing attacker: v1 uses plain local WS/HTTP. A later protocol version may negotiate authenticated encryption without changing the transfer state model.

### Text

`message_send`:

```json
{
  "id": "uuid",
  "conversationId": "smallerDeviceId:largerDeviceId",
  "senderId": "...",
  "receiverId": "...",
  "text": "Hello from LANVIA",
  "timestamp": 1786723200000,
  "status": "sent"
}
```

UTF-8 text maximum is 64 KiB. Store by `id` before acknowledging, making retries idempotent.

Text remains a plain UTF-8 wire field. Both clients render the same optional inline conventions without changing the envelope: `**bold**`, `*italic*`, `__underline__`, `~~strikethrough~~`, and `` `code` ``. Copy always places the original plain markup text on the clipboard; unsupported or unmatched markers are displayed literally.

`message_ack`:

```json
{ "messageId": "uuid", "status": "delivered" }
```

v1 statuses are `sending`, `sent`, `delivered`, `failed`. Offline messages remain local as `failed` with a retry action; LANVIA never relays via Internet.

### Transfer negotiation

`transfer_request`:

```json
{
  "transferId": "uuid",
  "fileName": "video.mp4",
  "mimeType": "video/mp4",
  "size": 125000000,
  "sha256": "64-lowercase-hex",
  "transferPort": 53212,
  "transferToken": "base64url-one-time-capability",
  "expiresAt": 1786723320000
}
```

The sender hashes and registers a source before requesting. The receiver never trusts `fileName` as a path: it takes a sanitized basename and resolves it beneath the configured download directory. Request expiry is 120 seconds.

`transfer_accept`: `{ "transferId": "uuid", "offset": 0 }`

`transfer_reject`: `{ "transferId": "uuid", "reason": "user_rejected" }`

`transfer_progress`:

```json
{
  "transferId": "uuid",
  "bytesTransferred": 53750000,
  "totalBytes": 125000000,
  "speed": 12400000,
  "remainingTime": 6
}
```

`speed` is bytes/second; `remainingTime` is integer seconds or `null` when unknown.

`transfer_pause`, `transfer_resume`, `transfer_cancel`: `{ "transferId": "uuid" }`, with resume additionally allowing `offset`.

`transfer_complete`: `{ "transferId": "uuid", "sha256": "...", "size": 125000000 }`

`transfer_error`: `{ "transferId": "uuid", "code": "hash_mismatch", "message": "Integrity verification failed", "retryable": true }`

### Keepalive

`ping`: `{ "nonce": "uuid" }`; `pong`: `{ "nonce": "same uuid" }`.

## 7. HTTP transfer

After `transfer_accept`, the receiver performs:

```http
GET /v1/transfers/<transferId> HTTP/1.1
Host: 192.168.2.152:53212
Authorization: Bearer <transferToken>
Range: bytes=<existing-part-size>-
X-LANVIA-Receiver: <receiverDeviceId>
```

Requirements:

* No directory path is accepted from HTTP. `transferId` maps to an in-memory/persisted approved source record.
* Token comparison is constant-time where the runtime permits.
* The source must be accepted, unexpired, and intended for `X-LANVIA-Receiver`.
* Without Range, return `200`; with a valid Range, return `206`, `Content-Range`, and `Accept-Ranges: bytes`.
* Invalid/unsatisfiable range returns `416`; auth returns `401`/`403`; missing/expired source returns `404`/`410`.
* The receiver writes `<safe-name>.lanvia.part`, never opens it, and atomically renames after exact size and SHA-256 verification.
* Redirects are not followed. The receiver connects only to the address associated with the peer control/discovery socket.
* Idle timeout is 30 seconds; decision timeout is 120 seconds; maximum 3 concurrent transfers by default.

Resume is receiver-driven: abort the GET to pause; preserve the part; send `transfer_pause`. Resume sends `transfer_resume` and a new Range GET. Cancellation deletes the part and invalidates the source capability.

## 8. Transfer state machine

```text
hashing -> pending -> accepted -> transferring -> verifying -> completed
   |          |          |            |              |
 failed   rejected   cancelled      paused         failed
                                      |  
                                      +-> transferring
```

Terminal states: `completed`, `rejected`, `cancelled`, `failed`. Invalid state transitions are ignored and logged. Both clients persist metadata, but never file bytes, in their database/store.

## 9. Errors, timeouts, and recovery

Common error codes are enumerated in `lanvia-protocol.json`. Network and parser failures are surfaced to diagnostics and UI; no socket callback may crash the process. A malformed peer is disconnected after a bounded error response/log entry. Logs exclude trust/transfer tokens and message/file contents.

On interface/address change:

1. mark existing peers offline and close sockets with 4002;
2. stop mDNS and UDP cleanly;
3. recompute active interfaces and broadcast addresses;
4. restart control/transfer listeners if necessary and restart discovery;
5. announce immediately, then reconnect eligible trusted peers.

## 10. Compatibility

A peer with envelope/discovery `version != 1` is shown as incompatible and is not connected. Minor app versions do not alter protocol behavior. New optional fields are permitted. New required semantics require protocol version 2.
